    Module 5 — Serverless Functions with OpenFaaS

    Status

    Beginner workshop under development; not yet validated or ready for delivery.

    This module is being authored in the Tutorials repository. Integration into edge-ai-blueprint, publication, and activation are separate later phases. Authoring does not change the current infrastructure or active workshop.

    The beginner material will be the complete reference implementation. An aligned advanced TODO version will be derived later.

    Learning objectives

    After completing the validated workshop, participants should be able to:

    • Explain HTTP request → OpenFaaS gateway → function → response, and distinguish the function developer's responsibilities from the platform provider's.
    • Invoke a prepared function and inspect HTTP status, headers, and JSON data.
    • Implement input validation and predictable successful and error responses.
    • Follow a controlled source → build → registry push → deployment workflow.
    • Distinguish changing request data from changing deployed function code.
    • Process deterministic weather data and handle external-service failures in an optional live-data extension.
    • Generate bounded local traffic, interpret verified metrics, and clean up only their assigned exercise resources.

    Serverless does not mean that servers disappear: the provider manages the runtime infrastructure. Cold starts may occur when an instance starts; they do not occur before every invocation. Scaling, scale-to-zero, queues, billing, and operator behaviour depend on the platform, edition, and configuration. JavaScript async/await is not queued asynchronous FaaS invocation. These features are not required exercises in this workshop.

    Participant journey

    The intended validated workshop begins with participants as developers in an organiser-prepared, isolated lab per participant or group. Participants will run complete guided build, push, deploy, invoke, update, and cleanup steps themselves. Installing Kubernetes, OpenFaaS, or monitoring is not part of the mandatory beginner path.

    A shared environment may be considered in a later advanced workshop for different learning objectives, including ownership, permissions, and collaboration.

    Starting environment and responsibilities

    Participants

    Participants need basic familiarity with HTTP/JSON and JavaScript, plus the ability to run guided Python cells and Bash commands. The organiser will prepare JupyterLab with a Python kernel, faas-cli, curl, Git, CA certificates, and the required Python packages. The retained-workspace exercises in Notebooks 2 and 3 require organiser-supplied Node.js 22 and npm on the notebook host. Their dependency-free handler tests require no participant npm install. Exact tool versions and the supported Node.js function runtime must be pinned and tested before delivery; do not reuse an end-of-life runtime. Apptainer remains an authoring test method, not the selected participant runtime.

    The planned execution environment is Linux with Bash in JupyterLab. Linux/amd64 is the initial reference target, not a claim of tested compatibility. Other host or image architectures require separate validation. The participant's laptop only needs a browser compatible with the prepared JupyterLab service; native macOS or Windows installation is not required. Exact browser versions remain to be tested.

    Notebook cells and notebook terminals run on the notebook host, not on the participant's laptop. In a notebook command, localhost means the notebook host; in a laptop browser, it means the laptop. The organiser must supply reachable notebook and browser routes instead of assuming they are interchangeable.

    Organisers

    Organisers prepare the reference platform, registry and protected builder, deploy initial functions, distribute configuration through an appropriate protected channel, verify readiness, and provide monitoring access. They retain platform administration and infrastructure-cleanup responsibilities.

    Participant access must be confined to the assigned disposable lab and registry repositories. Participants must not receive shared-platform administrator credentials, infrastructure-host Docker socket access, platform-admin kubeconfigs, or unrestricted registry credentials. Any administrative capability within the isolated lab must be documented explicitly.

    The isolation boundary, image-building capability, registry permissions, and scoped cleanup must be validated. Function-name prefixes alone are not authorisation.
